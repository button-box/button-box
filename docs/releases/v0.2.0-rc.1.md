# v0.2.0-rc.1 — Cloud test candidate

This candidate combines the Cloud runtime, local setup and dashboard changes,
and the fixes verified during a Raspberry Pi 4 Cloud regression campaign.
The installed program and prompt files match that tested runtime. This RC adds
an explicit fresh Cloud installer, release identity recording, and release
instructions. Fresh installation has separate checks from the runtime campaign.

This is an opt-in test candidate for additional units, not a stable release,
a disk image, an automatic update service, or certification of another unit.

## Included

- Cloud claim links, physical possession confirmation, and safe cancellation.
- Cloud owner-dashboard links and service-based readiness checks.
- Authorized voice download, ordered playback, and replies to the recent chat.
- Recordings bound to their original transport and Cloud account.
- Revoked-member checks that reject stale routes without another recipient fallback.
- NFC enrollment completion, cancellation, routing and durable operation receipts.
- Bounded updates that preserve the prior service state and retain program rollback.

## Evidence and limits

The final package includes a software-check receipt for the exact source.
The checks cover syntax, lint, Python and JavaScript behavior, and fresh-install
guards. These are software checks, not physical acceptance.

A live Cloud campaign verified receipt, ordered playback, duplicate inbox and
acknowledgment handling, replies, revoked-member guards, NFC routing, and service
restart recovery. Button and NFC events used controlled application inputs.
Real audio and provider delivery supplied separate evidence.

The following remain open or outside this candidate's acceptance:

- The genuine WhatsApp 24-hour closed-window template and approval flow awaits
  its real time boundary. It is not recorded as passed.
- Hosted Cloud outage and recording expiry, deletion and retention tests were
  deferred. Successful receipt does not establish retention behavior.
- The opening of a ringtone can be attenuated or have an altered pitch. This is
  an accepted minor limitation, not a passed audio test.
- The new fresh Cloud installation path needs its first real target-unit
  installation and claim acceptance. Isolated installer tests do not prove that.
- Standalone wacli regression, physical button and NFC reader operation, and
  cold power cycling need their own evidence on the target unit.

Keep these limits visible when reporting results. A successful installation
is not a complete messaging or hardware acceptance test.

## Required Cloud compatibility

Cloud mode requires the current authenticated device API v1 contract, including
account-scoped heartbeats and uploads, exact claim cancellation, and durable
message/command acknowledgments. The service must be compatible before the Pi
is updated. The public candidate does not include provider credentials or a
Cloud service deployment.

Older Cloud recordings without an account binding remain preserved and cannot
be sent automatically. A fresh heartbeat is required before new recording or
sending. Do not assign older recordings to the current account to bypass this
protection. See [Cloud runtime](../cloud-runtime.md).

## Package and installation

Use the attached device-source archive, `release-manifest.json`,
`installed-files.sha256` and `SHA256SUMS`. Start with the
[fresh Cloud guide](v0.2.0-rc.1-fresh-cloud.md) for a new unit. Use the
[candidate update guide](v0.2.0-rc.1-update.md) for an existing installation.
The manifest identifies all 86 installed program and prompt files.

An application update preserves the selected transport. An existing wacli box
stays in wacli mode. `messageboxctl enter-cloud-claim` is supported only for a
configured transitional Business box or an already prepared Cloud box; it is
not a general wacli migration command. The explicit fresh Cloud installer rejects
an existing application or private state. Standalone-to-Cloud conversion remains a separate migration and is not
performed by this candidate installer.

## Additional-unit acceptance

Record the exact candidate, compatible service, target hardware and prior state
before installation. Use the existing [acceptance matrix](../box-acceptance.md)
and [run template](../box-acceptance-run-template.md); do not copy another unit's
results as a new pass.

Verify fresh installation or update preservation and service health first. Then check setup,
record/review/send, authorized receipt and listening, correct reply recipient,
NFC routes, settings, revoked-member behavior and restart recovery. Keep
physical hardware checks separate from simulated application-input checks.
Run all work with the target owner's authorization and an approved test recipient.

For a defect report, include the version, hardware, steps and expected/actual
result. Exclude recordings, credentials, contact details, household identifiers
and private logs from public issues.
